# Phase 3.4 — Kernel Bootstrap Notes

**Date completed:** 2026-05-12
**Status:** Bootstrap complete. Kernel boots in VM; BCF refinement requests fire; cvc5 produces proofs; kernel rejects proof acceptance with `-ENOTSUPP` (expected — we deliberately skipped patch 0016, the proof-acceptance/resume half, since our bundle deltas replace it).

This document is the **runbook** for getting BCF's patched bpf-next kernel
booting on a Cloudlab box, in a state ready for our Phase 3.4 delta patches
to be applied on top. If the Cloudlab box ever rotates (per the
[no-pinned-Cloudlab feedback](#)) or the bootstrap state is lost, this
document is the recipe to redo it.

Time budget: **~3-4 hours** if everything goes smoothly. First-time
discovery took a full day because we found ~10 issues; this runbook should
let a re-do skip past them.

## Prerequisites checklist

Before starting:

- [ ] Cloudlab reservation that's stable for at least a few days.
- [ ] `gcc 11` or `gcc 12` available (`gcc --version`). Newer can also work
      but may surface `-Werror` warnings.
- [ ] Build deps: `git curl unzip make flex bison bc libssl-dev libelf-dev
      qemu-system-x86`. cvc5 build needs CMake + Java for ANTLR.
- [ ] At least **34 GB free** on local `/users/<you>` (kernel source + build).
- [ ] At least **70 GB free** somewhere (for the VM disk image — Cloudlab's
      `/proj/<your-project>` NFS usually has 100 GB).
- [ ] Read/write access to `/dev/kvm` (often needs `chmod 666 /dev/kvm` or
      `usermod -aG kvm $USER` once after node boot).

## Step-by-step

### Step 1: Clone BCF and run its build script through one failure

```bash
# Clone BCF
cd ~
git clone <BCF repo URL> BCF
cd BCF
```

Edit `scripts/build.sh` to **never re-clone bpf-next on retry**. Find this
block (around lines 38-52):

```bash
    if [[ -d "$kernel_dir" ]]; then
        ack "Removing existing kernel source at $kernel_dir"
        rm -rf "$kernel_dir" ...
    fi

    if [[ -n "$BPF_NEXT_COMMIT" ]]; then
        ack "Cloning bpf-next..."
        git clone ...
        git checkout -q "$BPF_NEXT_COMMIT" ...
```

Replace with:

```bash
    if [[ -d "$kernel_dir/.git" ]]; then
        ack "Reusing kernel tree at $kernel_dir (git reset to $BPF_NEXT_COMMIT)"
        pushd "$kernel_dir" > /dev/null
        git reset --hard "$BPF_NEXT_COMMIT" ...
        git clean -fdx ...
    else
        [[ -d "$kernel_dir" ]] && rm -rf "$kernel_dir"
        ack "Cloning bpf-next and checking out $BPF_NEXT_COMMIT"
        git clone "$BPF_NEXT_REPO_URL" "$kernel_dir" ...
        pushd "$kernel_dir" > /dev/null
        git checkout -q "$BPF_NEXT_COMMIT" ...
    fi
```

This means subsequent retries reset to pristine in ~3 seconds instead of
re-cloning in ~7 minutes.

### Step 2: Patch BCF's set1 patches that conflict with bpf-next at the pinned commit

BCF's patch series is authored against a slightly newer bpf-next than the
commit they claim as base (`4cb4897bb49a4`). Specifically, BCF expects a
field `struct bpf_iarray *gotox_tmp_buf` in `struct bpf_verifier_env` that
doesn't exist in our base, and `.clang-format` has different content.

**Edit `set1.../0002-bpf-Add-bcf_checker-top-level-workflow.patch`:**
Remove the entire `.clang-format` hunk:

```bash
sed -i '/^diff --git a\/.clang-format/,/^diff --git/{/^diff --git a\/include/!d}' \
   /users/<you>/BCF/patches-kernel/set1*/0002-bpf-Add-bcf_checker-top-level-workflow.patch
```

**Edit `set1.../0004-bpf-Add-top-level-workflow-of-bcf_refine.patch`:**
Remove the `gotox_tmp_buf` context line and fix the hunk count.

```bash
PATCH=/users/<you>/BCF/patches-kernel/set1*/0004-bpf-Add-top-level-workflow-of-bcf_refine.patch
sed -i \
  -e 's|^@@ -843,6 +855,7 @@ struct bpf_verifier_env {|@@ -843,5 +855,6 @@ struct bpf_verifier_env {|' \
  -e '/^	struct bpf_iarray \*gotox_tmp_buf;$/d' \
  "$PATCH"
```

#### 4c. Patch 0016 (set1) — skipped intentionally

#### 4d. Patch 0017 (set1) — index check fails (stacked-patch drift)

`git am --reject` does an upfront blob-hash check that fails because our
applied patches have modified `verifier.c` and `syscall.c`. Force-apply
manually:

```bash
git am --abort

PATCH=/users/<you>/BCF/patches-kernel/set1*/0017-*.patch
git apply --reject "$PATCH"
find . -name "*.rej"    # should print nothing for 0017
git add -A
AUTHOR=$(grep -m1 '^From:' "$PATCH" | sed 's/^From: //' | tr -d '\r')
DATE=$(grep -m1 '^Date:' "$PATCH" | sed 's/^Date: //' | tr -d '\r')
SUBJECT=$(grep -m1 '^Subject:' "$PATCH" | sed -E 's/^Subject: \[PATCH[^]]*\] //' | tr -d '\r')
git commit --author="$AUTHOR" --date="$DATE" -m "$SUBJECT"

/users/<you>/BCF/scripts/apply_all_patches.sh
```

#### 4e. Multiple `.clang-format` rejects in set2-set4

The apply script auto-handles these. No action.

Need to add `libbpf_set_prover` to `LIBBPF_1.7.0` block; the patch's

all libbpf files (`bpf.c`, `bpf.h`, `libbpf.c`, `libbpf.h`,

committed the staged file (`libbpf.map`); the other 5 had applied-but-
unstaged changes that were left in the working tree. Recovery:


### Step 6: Compile-time fix for the `bcf_release` function

After all patches apply, the kernel build will fail in `kernel/bpf/verifier.c`
in function `bcf_release` (BCF's anon-fd cleanup callback in 0015). Three
problems, all because the upstream bpf-next we're on lacks symbols/fields
BCF expected:

```bash
cd /users/<you>/BCF/build/bpf-next
sed -i '/clear_insn_aux_data(env, 0, env->prog->len);/d' kernel/bpf/verifier.c
sed -i '/release_insn_arrays(env);/d' kernel/bpf/verifier.c
sed -i '/kvfree(env->gotox_tmp_buf);/d' kernel/bpf/verifier.c

git add kernel/bpf/verifier.c
git commit -m "bpf: drop bcf_release calls to upstream helpers not in this base

bcf_release is the anon-fd cleanup callback in BCF's suspend/resume path
(patch 0015). Three of its calls reference upstream functions/fields not
yet in our pinned base 4cb4897bb49a4. Since our 3.4 deltas replace the
entire suspend/resume mechanism with bundle-lookup, this function is
dead code in our final flow; stub these three operations so the kernel
compiles."

git tag -f bcf-applied   # re-tag to include this commit
```

Inside the VM:

```bash

   /root/bcf/examples/unreachable_arsh.bpf.o \
   /sys/fs/bpf/test
```

**Expected outcome — `-ENOTSUPP` after cvc5 succeeds.** Not a failure; it's
proof that our setup works exactly as planned:

- `bcf requested, try to prove the path unreachable` → BCF refinement
  request fires (0015 is active).
- `Using prover: /usr/bin/cvc5` → libbpf BCF API works.
- `Proof produced: 715 steps, 17244 bytes` → cvc5 + the BCF format work.
- `BPF program load failed: -ENOTSUPP` → kernel has no code to **accept**
  the proof, because we deliberately skipped 0016 (the resume half).

This is **week-1 milestone 1 of Phase 3.4**: kernel infrastructure
proven; suspend-side intact; resume-side intentionally absent (replaced
by our bundle deltas).

## Lessons we learned the hard way

These bit us at least once during the bootstrap; capturing here so a re-do
skips them.

1. **`git am --3way` fails when blob hashes aren't in your repo.** BCF
   was authored on a slightly different bpf-next than they pinned; the
   `index abc..def` lines reference blobs we don't have. Use
   `git am --reject` instead.
2. **`git am --reject` does an upfront blob-hash check too.** Fails on
   any stacked patch where earlier patches modified the same files.
   Workaround: `git apply --reject` + manual commit with extracted
   metadata (see step 4d).
3. **`set -o pipefail` + `grep -q` is a footgun.** `grep -q` exits 0 on
   first match, sending SIGPIPE upstream; `pipefail` then makes the pipe
   return non-zero. Use process substitution: `grep -q "..." <(git log)`.
4. **`Subject:` lines in patch files often have CRLF.** Strip with
   `tr -d '\r'` before grepping/comparing.
5. **`git am --continue` only commits what's staged.** If you applied a
   patch with `--reject` and only `git add`-ed the file you manually
   fixed, the other files that applied cleanly are left in the working
   tree, uncommitted. Always `git status` after each `git am --continue`.
6. **`build.sh` wipes the kernel dir on every invocation.** Edit it to do
   `git reset --hard` instead (step 1).
7. **Cloudlab `/dev/shm` is only 32 GB but `boot_vm.sh` requests 64 GB.**
   Use `VM_MEM=16G ./scripts/boot_vm.sh`.
8. **`/dev/kvm` is root-only by default.** `chmod 666 /dev/kvm` (resets
   on reboot) or `usermod -aG kvm $USER` (persistent).
9. **The VM disk image is ~64 GB — too big for home.** Extract to
   `/proj/<your-project>/` (NFS) and symlink back.

## What comes next

Now that bootstrap is done, Phase 3.4 deltas:

1. Set up the local Mac → Cloudlab sync (git push to a remote on the
   Cloudlab box pointing at `/users/<you>/BCF/build/bpf-next`).
2. Write our deltas as new commits on top of `bcf-applied`:
   - 2-field `bpf_attr` extension (from
     [`c-ref/bpf_attr_bcf_ext.h`](../../c-ref/bpf_attr_bcf_ext.h))
   - `kernel/bpf/canonical_hash.c` (port of
     [`c-ref/canonical_hash.{h,c}`](../../c-ref/))
   - Bundle parser + hashmap construction in the verifier
   - Refinement-site lookup wiring (replaces what 0016 would have provided)
3. Rebuild kernel only, re-test in VM with a hand-built bundle on
   `shift_constraint.bpf.o`.

Reset point for iteration: `git reset --hard bcf-applied && git clean -fdx`
(~1 s). New patches go on top of `bcf-applied`; each test cycle is a
quick incremental `make -j` + VM reboot via `boot_vm.sh`.
